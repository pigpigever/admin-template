# Taste
- Prefers to be communicated with in Chinese. Confidence: 0.9
- Prefers tooling/config to follow widely-adopted industry best practices: asks the assistant to research common practices first (e.g. web search) before configuring rules/tools, rather than inventing its own set. Confidence: 0.55
- Wants the assistant to research options and lay out concrete alternatives (with trade-offs/tradeoff summaries) for the user to pick from, keeping the final decision himself, rather than having the assistant unilaterally choose a solution. Confidence: 0.7
- Prefers comprehensive/expansive lint rule coverage over a minimal conservative set: when given a modest linter config, pushes to enable more rules/plugins/categories (e.g. "规则太少了，再加多点"). Confidence: 0.7
- Wants code-style/quality conventions to be mechanically enforced by the linter (oxlint) rather than only documented or left to manual discipline. Confidence: 0.7
- Prefers dependencies kept on the latest major versions and is willing to upgrade proactively (e.g. chose antd v6 over staying on the stable v5 line) even when it forces adopting beta packages that are the only ones supporting the new major. Confidence: 0.6
- Wants project documentation organized as a centralized docs tree (`index.md` indexing all markdown docs, a `README.md` in every directory) and expects each docs subfolder to stay single-purpose — correcting the assistant when a folder accumulates mixed content, e.g. conventions/rules must live in their own directory (like `harness/`) while the design-doc folder holds only design/template material. Confidence: 0.7
- Prefers auxiliary/tooling directories to be dot-prefixed (hidden) rather than plainly named, e.g. renaming a docs `template/` folder to `.template/` and putting AI-guardrail scripts in a `.scripts/` directory. Confidence: 0.6
- Prefers TanStack Router's virtual file routes over plain file-based routing: wants the route tree explicitly declared in a config file (pointing at route files) with the generated route tree as build output, even though adding a page then means touching two places. Confidence: 0.6
- Prefers JSX/TSX callbacks longer than one line to be extracted into named functions instead of being inlined. Confidence: 0.8
- Wants component/element props with more than two props laid out on separate lines (one prop per line). Confidence: 0.8
- Dislikes hardcoded values; wants constants kept in a dedicated `constants` directory rather than defined inline. Confidence: 0.75
- Prefers `es-toolkit` for general-purpose utilities: when the library already provides a method (debounce, throttle, groupBy, chunk, uniq, pick, omit, clamp, etc.), use it instead of hand-rolling, and do not add lodash/underscore. Confidence: 0.8
- Wants each artifact type kept in its own dedicated top-level directory rather than colocated with source: all tests (unit/component) under a root `tests/` directory, custom oxlint plugins under `plugins/`, docs under `docs/` — and expects these placements to be enforced by AI guardrail/gate scripts. Confidence: 0.7
- Wants a design doc's change/revision history placed at the very top of the file with no heading, sorted newest-first. Confidence: 0.65
- Wants quality gates wired into the pre-commit hook so they run automatically on every commit, rather than being left to manual/CI invocation. Confidence: 0.6
- Wants lint plugins split by concern (one plugin per lint topic) instead of a single aggregated plugin, and all rule error messages / docs descriptions written in English. Confidence: 0.7
- Dislikes i18n where the code shows opaque keys (e.g. `i18n._("admin.dashboard.welcome")`) that don't match the rendered copy; prefers the actual source text to be visible in code, favoring the generated-ID / message-as-id approach over keeping stable key-based IDs. Confidence: 0.75
- Treats an all-warn lint config as a problem: prefers deterministic violations and hard project rules to be enforced at `error` (failing plain `pnpm lint`), reserving `warn` for subjective/style/heuristic rules. Confidence: 0.6
